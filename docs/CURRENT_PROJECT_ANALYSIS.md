## 1. Executive Summary

This repository hosts an Operations Research project aimed at determining optimal pit-stop and tyre-compound strategies in Formula 1 racing using mathematical programming. The project formulates two complementary optimization scopes:
1. **Scope 1 (MILP):** Single fastest race strategy minimizing total predicted race time.
2. **Scope 2 (Goal Programming):** Multi-objective balanced strategy trading minimal race time for fewer pit stops and reduced tyre degradation based on team priority weights.

Prior to this architectural phase, the repository contained raw historical data, an offline data build script, and the project presentation slides. This document analyzes the existing state, identifies reusable assets, and outlines the structural additions required for production-grade modularity.

## 3. Analysis of Existing Components

### 3.1 Existing Dataset (`data/processed/combined_dataset.csv`)
- **Origin:** Generated by merging Kaggle historical timing data with FastF1 tyre telemetry via `scripts/build_dataset.py`.
- **Coverage:** Complete coverage for 2018 through 2024 (148 races, 40 unique drivers, 16 constructor teams, 161,443 lap records).
- **Key Columns:**
  - `raceId` (int): Unique Kaggle race ID.
  - `Year` (int): Season year.
  - `Race` (str): Grand Prix name (e.g., "Australian Grand Prix").
  - `Driver` (str): 3-letter driver code (e.g., "HAM", "VER", "HAR").
  - `Team` (str): Constructor name.
  - `Lap` (int): Lap number within race.
  - `LapTime` (str): Lap time formatted as `M:SS.sss`.
  - `Position` (int): Track position after lap.
  - `Compound` (str): Active tyre compound (`SOFT`, `MEDIUM`, `HARD`, `ULTRASOFT`, etc.).
  - `TyreLife` (float): Age of tyre set in laps.
  - `Stint` (float): Stint sequence index (1, 2, 3...).
  - `pit_duration` (float): Pit stop duration in seconds (`NaN` on non-pit laps, populated on 5,098 laps).
- **Status:** **Complete, verified, and intact.** No re-generation or duplication is required.

### 3.2 Dataset Build Script (`scripts/build_dataset.py`)
- Reads raw CSVs from `data/raw/kaggle/` and `data/raw/fastf1/`.
- Merges on `[year, name, code, lap] == [Year, Race, Driver, Lap]`.
- Joins pit stop duration and constructor names.
- Writes to `data/processed/combined_dataset.csv`.
- **Status:** Fully functional offline script; serves as reproducible pipeline documentation. Must remain untouched.

### 3.3 Dependencies & Environment
- Previously had only a minimal `requirements.txt` containing `pandas>=2.0`.
- No virtual environment tracking, lockfile, modern build system (`pyproject.toml`), or package manager was configured.
- No frontend or backend existed.
- No unit tests or automated verification existed.

## 5. Architectural Deficiencies of Previous State

1. **Monolithic Data Access:** Without a standardized data layer, models would directly load and parse CSVs, leading to duplicate filtering and data leakage.
2. **Missing OR Model Implementations:** Neither Scope 1 (MILP) nor Scope 2 (Goal Programming) had code structures or abstractions.
3. **Absence of User Interface:** No UI was present to visualize strategy timelines, tyre degradation curves, or weight trade-offs.
4. **No API Bridge:** No backend existed to expose solver capabilities to interactive clients.
5. **Lack of Dependency & Lock Management:** Lack of pinned dependencies risked environment discrepancies across team members.
6. **No Automated Testing:** No test suite existed to verify mathematical constraints (e.g. stint limits, binary variables, deviation balance).

---

## 6. What Was Added in This Phase

To resolve these deficiencies without altering existing data or working code, the following architectural additions were established:

1. **Modern Python Environment with `uv`:**
   - Configured `pyproject.toml` with `hatchling` build backend.
   - Pinned Python 3.12 via `.python-version`.
   - Generated locked dependency graph in `uv.lock` with justified libraries (`pandas`, `numpy`, `scipy`, `pulp`, `pydantic`, `fastapi`, `uvicorn`, `pytest`).
2. **Modular Python Package (`src/f1_optimizer/`):**
   - `common/`: Shared data loaders, preprocessing, empirical statistics, degradation regression, race contexts, validation, schemas, and time utilities.
   - `scope1/`: Isolated MILP model, parameter structures, solver wrappers, output schemas, and service layer.
   - `scope2/`: Isolated Goal Programming model, target definitions, weight structures, deviation accounting, solver wrappers, and service layer.
   - `integration/`: Strategy comparison, trade-off analysis, and end-to-end orchestration pipeline.
   - `config/`: Centralized settings using Pydantic.
3. **Backend Service (`backend/`):**
   - FastAPI application scaffold (`app/main.py`, `app/api/`, `app/schemas/`, `app/services/`, `app/core/`).
   - Clean separation between API routes and mathematical solver core.
4. **Frontend Client (`frontend/`):**
   - React + TypeScript scaffold initialized with Vite.
   - Clean folder hierarchy for components, pages, layouts, hooks, services, types, and utils.
   - Type definitions matching backend and optimization schemas.
5. **Testing Architecture (`tests/`):**
   - Test suites mapped to `common/`, `scope1/`, `scope2/`, and `integration/`.
   - Verified active pytest environment passing smoke tests.
6. **Documentation Suite (`docs/`):**
   - `CURRENT_PROJECT_ANALYSIS.md` (this file).
   - `PROJECT_PLAN.md` (detailed multi-phase implementation roadmap).
   - `ARCHITECTURE.md` (concise architectural reference with Mermaid diagrams).
   - `mathematical-models/` (mathematical specifications for both scopes).
